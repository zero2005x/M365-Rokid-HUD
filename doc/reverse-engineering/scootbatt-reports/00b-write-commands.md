# Scootbatt 協定逆向 — 第 2 部分：寫入命令清單（解鎖／限速／設定）

> ⚠️ **全部為靜態分析結果，未經任何實車驗證。寫入命令有實質風險，切勿直接對真實車輛發送。**
>
> 目標：Scootbatt 1.9.2 (136)。來源：`jadx-out/sources/`、`apktool-smali/smali/`。
>
> **修訂紀錄**：初稿（00b 版）有以下錯誤，本版已更正 ——
> ① 誤把 `0x75`/`0x77` 寫入列為功能（實為本 build 的死碼）；
> ② 誤把 SHFW 寫入位置寫成 `0xD4`（實為 **`0xB2`**）；
> ③ 誤標 `0x7B`=訊號品質、`0x7C`=錯誤碼（實為 **KERS / 巡航**，我把 case 編號搞混）；
> ④ 誤稱「共 11 條」（實為 **16 條** user-visible 寫入）。

## 1. 完整寫入命令表（16 條，全部 `direction = 0x20`）

內層框一律為 `3E 20 <action> <position> <payload…>`，再由 `pe4.m12550k()` 加外層信封與
checksum（見第 1 部分 §2.2）。

### 1.1 原廠 register 寫入（action `WRITE` = `0x02`）

| # | 功能 | position | payload | 可逆 | 風險 | 證據 |
|---|---|---|---|---|---|---|
| W1 | **鎖車** | `0x70` (112) | `{01, 00}` | ✅（W2） | 中 | `p000/vc2.java:41` |
| W2 | **解鎖** | `0x71` (113) | `{01, 00}` | ✅（W1） | 中 | `p000/vc2.java:43` |
| W3 | KERS 弱 | `0x7B` (123) | `{00, 00}` | ✅ | 低 | `p000/tr4.java:142` |
| W4 | KERS 中 | `0x7B` | `{01, 00}` | ✅ | 低 | `p000/rs1.java:216` |
| W5 | KERS 強 | `0x7B` | `{02, 00}` | ✅ | 低—中 | `p000/s49.java:176` |
| W6 | **巡航關** | `0x7C` (124) | `{00, 00}` | ✅ | 中 | `p000/zk0.java:35` |
| W7 | **巡航開** | `0x7C` | `{01, 00}` | ✅ | **中—高** | `p000/al0.java:40` |
| W8 | 尾燈 **開** | `0x7D` (125) | `{hi, lo}`，bit1 | ✅ | **高**（見 §3.3） | `p000/nj7.java:171` |

| # | 功能 | position | payload | 證據 |

## 2. 完整性如何證明（不是猜的）

- `mo777f()`（SHFW 寫入的唯一出口）在整個 App 內**只有一個呼叫者**：
  `p000/C1312th.java:439`。
- 該呼叫者只由 **21 個 `WriteRegisterRequestEvent` 站點**餵入。
- 所有 `writeCharacteristic` 站點已逐一列舉。
- 因此「16 條」是**窮舉結果**，而非取樣。

`0x75 {1,0}` 與 `0x77 {1,0}` 的寫入建構子存在於 `p000/r36.java:166` 與
`p000/C0059ay.java:450`，但**沒有任何可達的建構路徑**（`yq0` 角色無建構站點），
且 `0x75` 在本 App 中**只被讀取**（Normal/ECO/Sport，`C1138os` case 11，
對應 `dp3.java:347`）→ 判定為**死碼**。

## 3. 風險標註（依嚴重度排序）

### 3.1 W12 — SHFW profile 切換（最高）

改變**正在生效的自訂韌體參數組**（速度限制、電流、KERS 等）。
profile 名稱是透過**已匯出、無權限保護的廣播接收器 `SHFWProfileNamesReceiver`** 取得的，
因此若使用者看到的名稱清單過期／被偽造，可能選到**不是他看到的那個 index**。
送出兩次、無 ACK、無讀回。

### 3.2 W7 — 巡航控制開啟

屬安全相關功能，**沒有確認對話框、沒有靜止狀態檢查**。

### 3.3 W8–W11 — register `0x7D` 的位元組序不一致（最可能的「寫錯值」）

| 路徑 | 位元組序 | 證據 |
|---|---|---|
| **讀取** | **小端** `u16` | `AbstractC1491y9.java:498`（`LITTLE_ENDIAN.getShort()`） |
| **寫入** | **大端** `{hi, lo}` | `p000/nj7.java:171`（`intValue >>> 8` 先送） |

而且尾燈（bit1）與 mph 單位（bit4）**共用同一個 16-bit 字**。位元組序搞錯時，
不只設定失敗，還可能**污染相鄰位元甚至波及 register `0x7E`**。
→ 這是原廠命令集中最危險的一條。

### 3.4 W13–W16 — SHFW 設定寫入的位址不一致（未解）

- 寫入後**沒有讀回**（`kd4`/`wv3`/`ed2` 都回傳 `null`）。
- App **讀取**這些欄位用的是 block offset 10..15（register `base+26`..`base+31`），
  但**寫入**用的是 `base+21/22/23` —— **存在 5–7 byte 的位址不一致，尚未釐清**。
- → 整合時**必須直接採用寫入位址**，不可把讀取推導出的 offset 當成寫入位址。

## 4. 明確不存在的危險命令（好消息）

窮舉後確認本 App **沒有**任何 brick 等級命令：

- ❌ 無 OTA / DFU / flash / EEPROM 寫入
- ❌ 無序號寫入、無地區（region）寫入
- ❌ **完全沒有 BMS 寫入** —— 所有 `0x22` / `0x23` 方向的請求都是 `READ`
- ❌ 無速度限制寫入、無輪徑寫入

所有寫入都是 **≤2 byte 的設定 register 寫入**，只要知道舊值即可還原；
但**App 本身沒有 undo／歷史紀錄**。

## 5. App 自身的防護機制（整合時值得照抄）

| 機制 | 說明 | 證據 |
|---|---|---|
| 鎖定列隱藏 | `g2`/`g65`/`f2` 隱藏鎖定 UI | `Scooter.isNewNinebotGeneration()` |
| SHFW 列條件顯示 | 只在偵測到 SHFW（旗標 `f30561r0`）且已收到 profile 名稱時才顯示 | — |
| 未讀取前禁用開關 | 必須先讀過對應 register 才能操作（required-observables）；並用 `setCheckedNoEvent` 避免讀回觸發再寫入 | `h84`/`xb2` |

| 原廠寫入有讀回驗證 | KERS→`0x7B`、燈光/單位→`0x7D`、鎖→`0xB2` | — |

## 6. 認證需求（決定第三方程式能否寫入）

| 車型 | 寫入是否需要認證 |
|---|---|
| 明文 `Ninebot`（`5A A5` + 16-bit 一補數 checksum） | **不需要** —— 可 byte-for-byte 重現 |
| 明文 `Xiaomi`（`55 AA`） | **不需要** |
| `NinebotCrypto`（廣告 byte[1]==2 → `Scooter.useCrypto`） | **需要** `5B/5C/5D` 金鑰交換 + `C1375v6` 密碼器 |
| Xiaomi 橢圓（曝露 `0000fe95`） | **需要** ECDH secp256r1 + AES-CCM，且需 `beaconKey`/`deviceInfo`/`deviceToken` |

## 7. 未驗證 / 需要實車

1. `0x7D` 的位元組序與 bitfield 寬度（讀小端／寫大端的矛盾）。
2. SHFW register 語意與合法值域；`0xB2 = 0` 是否代表「原廠 profile」。
3. Xiaomi 框的長度 byte（App 用 payload+2，既有文件說 payload+3）。
4. 設定是否跨斷電保存。
5. 車輛對越界 KERS／巡航值的容忍度。
6. W13–W16 寫入位址與讀取 offset 的 5–7 byte 不一致。
7. 每條寫入「送 3 次」的確切間隔與失敗處理。
